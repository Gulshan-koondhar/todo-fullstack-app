# Phase IV – Local Kubernetes Deployment (Spec-Driven Development) Constitution

## Core Principles

### I. Spec-Driven Deployment Only (Kubernetes Manifests via Claude Code)
All Kubernetes manifests, Dockerfiles, and Helm templates MUST be generated exclusively by Claude Code from refined specs. No manual editing of YAML, Dockerfiles, or Helm files is permitted — only spec iteration is allowed. All deployment components MUST be generated from specifications through the Claude Code workflow.

**Rationale**: Ensures deterministic, traceable deployment configurations while maintaining separation of concerns between infrastructure definitions and manual intervention.

### II. Stateless Architecture with External State Persistence
All application components MUST be stateless with all persistent state stored externally in Neon PostgreSQL. Application pods MUST be able to restart without losing conversation state or user data. Database connections MUST be managed via environment variables and Kubernetes Secrets. Clear separation between application state and persistent data storage.

**Rationale**: Ensures horizontal scalability, resilience to pod restarts, and proper cloud-native architecture patterns.

### III. Security-First Approach with Kubernetes Secrets Management
Sensitive values (API keys, DB credentials, JWT secrets) MUST be managed exclusively via Kubernetes Secrets. Secrets and environment variables MUST never be hardcoded in code or manifests. All sensitive configuration MUST be injected at runtime through Kubernetes mechanisms. No plaintext secrets in source code or deployment files.

**Rationale**: Ensures secure handling of sensitive data and prevents accidental exposure of credentials.

### IV. Reusability of Infrastructure Intelligence Through Helm
Infrastructure intelligence MUST be reusable through Helm subcharts and deployment blueprints. Helm charts MUST be structured for reusability with values overrides and subcharts where applicable. All Kubernetes deployments MUST leverage Helm for consistent, configurable deployment experiences.

**Rationale**: Enables rapid deployment across environments and promotes infrastructure-as-code best practices.

### V. Cloud-Native Readiness and Scalability
Applications MUST be designed for cloud-native readiness including horizontal scalability and resilience to pod restarts. Observability MUST be implemented via AIOps tools and standard Kubernetes monitoring. Applications MUST gracefully handle scale-out and scale-in operations.

**Rationale**: Ensures the system can grow with demand and maintain availability during infrastructure changes.

### VI. AIOps-Assisted Operations and Automation
AIOps tools MUST be leveraged for manifest generation, troubleshooting, and scaling operations. Usage of kubectl-ai and kagent MUST be documented in specifications. All AIOps prompts and interactions MUST be recorded for reproducibility and learning.

**Rationale**: Accelerates operations and reduces manual intervention while building institutional knowledge.

## Technology Stack & Constraints

### Locked Technology Stack
- **Orchestration**: Kubernetes with Minikube (local cluster only)
- **Container Runtime**: Docker images built locally and loaded into Minikube
- **Package Manager**: Helm 3.x for Kubernetes deployments
- **Database**: Neon Serverless PostgreSQL (external persistence)
- **Exposure**: Minikube service, tunnel, or Ingress (no external cloud load balancers)
- **Development Tool**: Claude Code for all manifest and Dockerfile generation

### Kubernetes Deployment Requirements
- All Kubernetes manifests MUST be generated by Claude Code from specs
- Docker images MUST use multi-stage builds for optimization
- Helm charts MUST support configurable values for different environments
- Deployments MUST include proper resource limits and requests
- Services MUST be configured for proper internal communication

### Security Requirements
- All sensitive data MUST be stored in Kubernetes Secrets
- No hardcoded credentials in any deployment files
- Proper RBAC configurations MUST be defined for all components
- Network policies SHOULD be implemented for enhanced security
- Pod security standards MUST be followed

### Container Requirements
- Every deployment component (frontend, backend, MCP server) MUST be containerized
- Dockerfiles MUST use multi-stage builds for security and efficiency
- Images MUST be built locally and loaded into Minikube
- Proper health checks MUST be implemented for all services
- Proper startup probes MUST be configured for all applications

### Statelessness Requirements
- Applications MUST not store state in pod filesystems
- Session data MUST be persisted in external Neon PostgreSQL
- Cache data MUST be managed by external services or memory-only
- All user data MUST persist independently of pod lifecycle
- Pod restarts MUST not result in data loss

### AIOps Integration Requirements
- AIOps tools usage MUST be documented in specs
- Prompts used with kubectl-ai/kagent MUST be recorded
- AIOps-generated resources MUST be validated before deployment
- At least one resource MUST be generated using AIOps tools
- Troubleshooting activities MUST leverage AIOps where applicable

### Monorepo Organization
- Docker files: `/docker/` directory
- Helm charts: `/helm/` directory
- Kubernetes raw manifests (optional): `/k8s/raw/` directory
- Specs: `/specs/deployment-phase-iv/` directory
- All changes MUST preserve Phase III functionality

### Functional Constraints
- Local cluster only: Minikube (no cloud K8s in this phase)
- No new backend features or AI logic changes — only deployment & orchestration
- All Phase III functionality MUST remain preserved (stateless chat endpoint, AI agent + MCP tools)
- Exposure limited to Minikube service, tunnel, or Ingress

## Success Criteria

### Deployment Validation
- Full application (login, task CRUD, AI chatbot) runs reliably inside Minikube
- Kubernetes manifests deploy without errors
- All services are accessible within the cluster
- External database connections are properly established

### Statelessness Validation
- Stateless behavior validated: pod restarts do not lose conversation state (persisted in Neon DB)
- Data persists across pod restarts and scaling operations
- No data corruption during scaling events
- Consistent user experience regardless of pod placement

### Security Validation
- Secrets properly injected and used (DB connection, OpenAI key, JWT)
- No plaintext secrets visible in Kubernetes resources
- Proper access controls implemented
- Security scanning passes without high/critical vulnerabilities

### Scalability Validation
- Basic scaling demonstrated (multiple replicas of backend)
- Load distribution works correctly across replicas
- Resource utilization remains stable during scaling
- Horizontal Pod Autoscaler configured where appropriate

### AIOps Integration Validation
- AIOps tools used to generate or debug at least one resource
- kubectl-ai or kagent commands successfully executed
- AIOps-generated configurations are functional
- Documentation of AIOps usage included in specs

### Demo Validation
- Demo video shows: minikube start, helm install, app access, task/chat interaction, pod restart resilience
- Complete spec → generation → commit history proving iterative, non-manual development
- All Phase III functionality remains operational
- No manual edits to generated files

## Governance

### Constitution Authority
This constitution supersedes all other practices and guidelines in the project. All development decisions MUST be evaluated against these principles. Any ambiguity MUST be resolved by prioritizing security, statelessness, and spec-driven workflow.

### Amendment Process
1. Propose amendment with clear justification and impact analysis
2. Document the change rationale, affected artifacts, and migration strategy
3. Verify that changes do not violate core security and statelessness principles
4. Update constitution version following semantic versioning:
   - MAJOR: Backward-incompatible principle removals or redefinitions
   - MINOR: New principle added or material expansion of guidance
   - PATCH: Clarifications, wording fixes, non-semantic refinements
5. Propagate changes to dependent templates (plan, spec, tasks)
6. Maintain full amendment history in governance section

### Compliance Verification
- All PRs MUST verify compliance with constitution principles
- Complexity or deviations from principles MUST be explicitly justified
- Constitution Check in plan.md MUST be completed before implementation
- Any bypass of spec-driven workflow MUST be documented and approved
- Kubernetes best practices MUST be verified before deployment

### Runtime Development Guidance
Use CLAUDE.md in the repository root for agent-specific runtime guidance. Constitution provides the principles; CLAUDE.md provides operational context for Kubernetes deployment.
